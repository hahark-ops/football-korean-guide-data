# 라이브 점수 지연 측정 (2단계 준비)

## 목적

balldontlie NFL API의 진행 중 경기 점수가 실제 플레이보다 얼마나 늦게 바뀌는지 잰다. AGENTS.md의 실시간 데이터 게이트는 "실시간"이나 "LIVE"라고 표시하기 전에 갱신 속도를 실제로 측정하도록 요구한다.

- 30초 안팎이면 실시간 점수로 안내할 수 있다.
- 몇 분씩 늦으면 "몇 분 늦을 수 있어요"처럼 표시하거나 유료 등급을 검토한다.

## 왜 경기 중에 재야 하나

API는 현재 점수만 주고 점수가 바뀐 시각은 남기지 않는다. 그래서 경기 중에 20초 간격으로 조회해 바뀐 시각을 기록한다. 그 뒤 다음 날 nflverse play-by-play의 `time_of_day`(플레이의 실제 시각)와 비교한다.

## 확인한 사실 (2026-10-07)

- 무료 등급: 분당 5회, `games` 조회 포함. 응답에 `status_state`(scheduled, in_progress, final 등), 총점, 쿼터별 점수가 있다. 진행 중 쿼터와 남은 시간은 `status` 문자열에 담긴다(경기 중 형식은 미확인).
- `dates[]` 조건은 UTC 날짜 기준이다. 목요일 밤 8:15 ET 경기는 `2026-10-09`로 조회한다(2026-10-07에 실제 응답으로 확인: TB@DAL 00:15Z가 이 날짜에 나온다).
- 키는 사용자가 `.env.local`의 `BALLDONTLIE_API_KEY`에 저장했다. 앱 번들에 들어가지 않도록 `VITE_`를 붙이지 않는다. 스크립트는 키를 출력하지 않는다.
- balldontlie 이용약관(2026-09-17 개정판, 2026-10-07 확인): 6조는 데이터의 저장, 가공, 게시, 배포를 허용한다. 가공하지 않은 원 데이터를 파는 것과 balldontlie와 경쟁하는 서비스를 만드는 것은 금지한다. 11조는 경기 사실(점수 등)의 소유를 주장하지 않으며, 리그 등 제3자 권리는 이용자가 직접 확인할 책임이라고 적는다. 그래서 NFL 쪽 권리는 여전히 미확인이고, 공개 저장소에는 아래의 변화 기록만 남긴다.

## 클라우드 자동 실행 (데이터 저장소의 GitHub Actions)

사용자의 노트북은 경기 시간대(한국 새벽~오전)에 꺼져 있는 경우가 많아서, 측정은 공개 데이터 저장소의 `live-probe` 워크플로가 대신 돌린다. 워크플로 원본은 앱 저장소의 `pipeline/data-repo/.github/workflows/live-probe.yml`이다.

| 대상 경기 | cron (UTC) | 한국 시각 | 조회 날짜(UTC) |
| --- | --- | --- | --- |
| 일요일 낮 경기 (동부 오후 1시) | `20 16 * * 0` | 월 01:20 | 일요일 |
| 일요일 늦은 오후 경기 (동부 4:05/4:25) | `40 19 * * 0` | 월 04:40 (실제 시작은 앞 실행이 끝나는 월 07:00 무렵) | 일요일 |
| 선데이 나이트 | `35 23 * * 0` | 월 08:35 | 월요일 |
| 먼데이 나이트 | `35 23 * * 1` | 화 08:35 | 화요일 |
| 서스데이 나이트 | `35 23 * * 4` | 금 08:35 | 금요일 |

- 조회 날짜는 실행이 시작된 시각에서 **1시간 뒤의 UTC 날짜**다. 그래서 밤 경기 실행이 전날 23:35 UTC에 시작해도 다음 날(경기 날) 날짜를 조회한다. GitHub 예약 실행이 가장 많이 밀리는 정시(특히 00:00 UTC) 직후를 피하고, 첫 경기(서머타임 중 00:15/00:20 UTC)까지 40분 넘게 여유를 둔다. 스크립트가 첫 경기 10분 전까지 기다린다.
- 모든 실행은 같은 concurrency 그룹이라 동시에 돌지 않는다. 앞 실행이 도는 중에 다음 예약이 오면 끝날 때까지 기다렸다가 이어서 돈다(조회 횟수가 무료 한도 분당 5회를 넘지 않게). 일요일 늦은 오후 실행은 이 방식으로 낮 실행이 멈춘 22:00 UTC 무렵부터 늦은 경기가 끝날 때까지 기록하고, 선데이 나이트 실행은 그 뒤에 시작한다.
- 실행마다 `--interval 20 --max-minutes 340`으로 돈다. GitHub 작업 제한(6시간, 워크플로에는 355분)보다 먼저 스스로 멈춘다. 첫 경기가 그 340분 뒤라면 기다리지 않고 바로 끝낸다.
- 미국 서머타임이 끝나는 2026-11-01부터는 경기가 UTC로 1시간 늦어진다(낮 경기 18:00 UTC, 한국 새벽 3시). 스크립트가 첫 경기 시각에 맞춰 기다리므로 cron은 그대로 둔다.
- 키는 저장소 Secret `BALLDONTLIE_API_KEY`에 둔다. Secret이 없으면 안내만 남기고 성공으로 끝난다.
- Actions 탭에서 `live-probe`를 직접 실행할 때 `date`(UTC 날짜)를 넣을 수 있다. 비우면 실행 시점에서 1시간 뒤의 UTC 날짜다.

### 기록 범위 (2026 정규 시즌 272경기로 시뮬레이션, 2026-10-07)

경기 길이 195분, 실행 사이 준비와 커밋 2분을 가정했다.

- 거의 전부 기록(98% 이상): 256경기. 일요일 늦은 경기는 낮 실행에서 늦은 오후 실행으로 넘어가는 2분 정도가 빈다.
- 일부만 기록: 런던 등 해외 아침 경기(동부 9:30) 6경기. 일요일 낮 실행이 시작될 때 이미 끝나 가고 있어 마지막 25~85분만 남는다.
- 기록하지 못함: 10경기. 정해진 요일 밖의 경기다.
  - 수요일 경기: 개막전(9/9), 추수감사절 전날(11/25)
  - 추수감사절 낮 경기 2개(11/26 동부 1:00, 4:30). 추수감사절 밤 경기는 목요일 밤 실행이 기록한다.
  - 블랙프라이데이 낮 경기(11/27 동부 3:00)
  - 토요일 경기 2개(12/19 동부 5:00, 8:20)
  - 크리스마스 경기 3개(12/25 동부 1:00, 4:30, 8:15)
  - 시즌 막바지 토요일 경기와 플레이오프(1월)는 이 시뮬레이션에 넣지 않았다. 플레이오프의 토요일 경기도 기록하지 못한다.
- GitHub 예약 실행이 15분 늦어져도 결과는 같다. 30분 늦어지면 해외 아침 경기 4개를 놓친다(98% 이상 기록은 256경기 그대로).
- 측정은 지연 표본을 모으는 것이 목적이라 빠지는 경기를 위한 예약은 따로 두지 않았다. 필요하면 해당 날짜로 직접 실행한다.

### 공개 저장소에 남기는 것

- 원본 기록(조회마다 받은 응답 전체)은 실행 안에서만 쓰고 커밋하지 않는다. `summarize-log.mjs`가 원본에서 **변화 기록**만 뽑고, 그것만 데이터 저장소의 `probe-logs` 브랜치 `changes/<날짜>.jsonl`에 커밋한다. 같은 날짜를 다시 돌리면 뒤에 이어 붙는다. `main`과 앱에는 들어가지 않는다.
- 변화 기록에는 경기(`TB@DAL`), 시작 시각, 상태(`scheduled`, `in_progress`, `final`)나 점수가 바뀐 것을 처음 본 시각(`seenAt`), 바로 앞 조회 시각(`prevPollAt`), 바뀐 상태와 더해진 점수(`awayPts`, `homePts`)만 들어간다. 경기 도중에 시작한 실행은 처음 본 점수(`scoreAtFirstSeen`)도 남긴다. 실행마다 첫 줄은 조회 횟수, 실패 횟수, 가장 긴 조회 간격 같은 실행 정보다.
- balldontlie의 경기 ID, `status` 문자열(쿼터와 남은 시간), 쿼터별 점수, 조회마다의 응답은 남기지 않는다. 점수 자체는 nflverse play-by-play에도 플레이마다 있는 경기 사실(CC BY 4.0)이고, 시각은 이 측정이 잰 값이다.
- 그 결과 변화가 실제로 API에 반영된 시각은 `prevPollAt`보다 늦고 `seenAt`보다 이르다. 지연은 이 구간과 nflverse `time_of_day`를 비교해 구한다.

## 직접 실행

```bash
node research/live/log-scores.mjs --date 2026-10-11 [--interval 20] [--max-minutes 360]
node research/live/summarize-log.mjs research/live/logs/2026-10-11.jsonl
```

- 키는 환경 변수 `BALLDONTLIE_API_KEY`를 먼저 보고, 없으면 저장소 루트의 `.env.local`에서 읽는다.
- 첫 경기 10분 전까지 기다렸다가, 모든 경기가 끝난 뒤 10분 또는 마지막 경기 시작 4시간 반 뒤까지 기록한다. `--max-minutes`(기본 360)는 기다리는 시간까지 포함한 전체 실행 시간의 상한이다.
- 그 날짜에 경기가 없거나(쉬는 날, 비시즌) 첫 경기가 `--max-minutes` 뒤라면 한 번 조회한 기록만 남기고 exit 0으로 끝난다(Windows의 Node 24에서 실제 API로 확인). 첫 조회가 실패하면 1분 간격으로 두 번 더 시도한다.
- 원본 기록은 `research/live/logs/<날짜>.jsonl`에 남고 git에서 제외된다. 줄마다 조회 한 번이며, 마지막 줄 `{"stoppedAt", "reason"}`은 멈춘 이유(`all games final`, `4.5 hours after the last kickoff`, `max-minutes`, `no games`, `first kickoff after max-minutes`)다.
- `summarize-log.mjs`는 공개 저장소에 올라가는 것과 같은 변화 기록을 표준 출력으로 낸다. 경기를 두 번 이상 조회하지 못한 기록이면 아무것도 내지 않는다.
- Windows에서는 실행 중에만 절전을 막는다. 뚜껑을 닫으면 잠들 수 있다.
